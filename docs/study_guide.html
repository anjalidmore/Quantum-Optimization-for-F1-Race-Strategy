    Knowledge Representation

    An F1 ontology and knowledge graph built from one declarative schema.

    What and whyHow it works, step by stepTechnologiesKey functionsCode walkthroughOutputs and examplesApplicationsKey points & viva

    What and why

    Practical 1 models the Formula 1 domain explicitly: 61 entities (Season, Race, Driver, Stint, PitStop, TyreCompound, ...) grouped into 12 categories, their typed attributes, and 29 relationships with cardinalities.

    Why: a shared, machine-readable vocabulary makes the domain inspectable before any model is trained, and gives every later artefact (OWL file, graphs, tables, validation report) one definition to agree with. The design rule in schema.py is that nothing hard-codes an entity or relationship twice — the ontology, both graphs and all five reports are generated from the same tuples.

    Run it

    python scripts/build_knowledge_base.py

    How it works, step by step

    1. Declare the domain as data

      schema.py defines Entity, Attribute and Relationship as frozen dataclasses and lists the whole domain in two tuples, ENTITIES and RELATIONSHIPS. Each attribute carries a DataType (mapped to XSD later) and each relationship a Cardinality.

    2. Build the OWL ontology

      build_ontology creates one root class per category (suffixed Category so the Weather category cannot collide with the Weather entity), then entity classes — roots first, so a child's parent class always exists. Attributes become DataPropertys named Entity_attribute with an XSD range; relationships become ObjectPropertys. Cardinality is encoded as OWL characteristics: many-to-one and one-to-one are FunctionalProperty, one-to-one is also InverseFunctionalProperty. The result is saved as RDF/XML.

    3. Build two graphs

      build_schema_graph turns the schema into a NetworkX MultiDiGraph (a multigraph, because two entities can be linked by more than one named relationship). build_instance_graph populates a small sample race (the ABox), and instance_graph_to_rdf serialises it as RDF triples with rdf:type and rdfs:label for Turtle export.

    4. Validate the model

      run_all_checks runs the suite in validation.py: unique entity and relationship names, every relationship endpoint exists, every declared parent exists, no orphan entities, and the instance graph conforms to the schema. The driver script exits non-zero on any failure, so it doubles as a CI gate.

    5. Render and report

      visualize.py draws the schema and instance graphs as PNGs and emits a Mermaid source file; reports.py writes the entity, attribute, relationship, ontology and validation tables as Markdown.

    Key points & viva

    Why generate every deliverable from one schema?

    Single source of truth: the tables, the ontology and both graphs all derive from schema.py, so adding an entity or relationship in one place updates every deliverable on the next run.

    How is cardinality represented in OWL?

    Many-to-one and one-to-one relationships become FunctionalProperty; one-to-one is also InverseFunctionalProperty, so an OWL reasoner can enforce the intended multiplicity.

    Why is the instance validation subclass-aware?

    _subclass_closure resolves each entity's descendants, so an edge whose declared range is TrackStatus legitimately accepts a SafetyCar individual.

    What does an entity's source field record?

    Whether it comes from the Kaggle historical schema, FastF1, or both — provenance carried into the data-engineering practical.

    Rule-Based Expert System

    32 production rules with forward and backward chaining, and an explanation for every firing.

    What and whyHow it works, step by stepTechnologiesKey functionsCode walkthroughOutputs and examplesApplicationsKey points & viva

    What and why

    Practical 2 encodes race-strategy expertise as 32 IF–THEN rules in 10 categories (weather, safety car, tyre, pit, strategy, ...), and an inference engine that derives decisions such as pit_decision, recommended_tyre and risk_level from a race state.

    Why: some strategy knowledge is categorical and well understood — a safety car makes a stop cheap, standing water needs full wets — and a statistical model trained on one dry race could never learn it. Rules also explain themselves: every derived fact records which rule produced it and which conditions held. In Practical 9 the rule verdict takes precedence over the ML models for exactly this reason.

    Run it

    python scripts/run_expert_system.py

    How it works, step by step

    1. Rules are data, not if-statements

      rules_schema.py defines Condition (fact <operator> value), Action (set key = value, with an optional confidence) and Rule (conditions, connective ALL/ANY, actions, salience). rule_base.py lists the rules with the rule(), cond() and act() shorthands.

    2. Closed-world condition evaluation

      Condition.evaluate returns False for a missing or None fact and for incomparable types, so a rule never fires on data it does not have.

    3. Working memory with provenance

      WorkingMemory stores each fact with its provenance (input or derived) and the rule that asserted it. assert_fact returns whether memory actually changed — the signal the engine uses to detect a fixed point.

    4. Forward chaining (data-driven)

      Each iteration, forward_chain collects every satisfied rule (the conflict set), orders it by the chosen strategy — by default salience, then specificity (more conditions wins), then rule id — and fires the rules that still change memory. A rule/value signature stops identical re-firings. It stops at a fixed point or after 200 iterations. notes accumulate instead of overwriting.

    5. Backward chaining (goal-driven)

      backward_chain proves a goal such as pit_decision == 'PIT_NOW': it finds rules that assert it, checks each condition against the facts, recurses on equality conditions it cannot yet satisfy, and returns a ProofNode tree. A visited set stops cycles.

    6. Validate and explain

      validate_rule_base checks unique ids, non-empty rules, registered fact keys, operator/value sanity, confidence bounds, and contradictions (identical antecedents and salience asserting different values). Explainer.justify answers how a fact was derived: the rule, the conditions that held and the supporting facts.

    State-Space Search

    Pit strategy as a shortest-path problem, solved by BFS, DFS, UCS, Greedy and A*.

    What and whyHow it works, step by stepTechnologiesKey functionsCode walkthroughOutputs and examplesApplications

    What and why

    Practical 3 casts strategy as search over race states: from lap 0 on the start tyre, choose at every lap whether to run on or pit for a compound, so that the full distance takes the least estimated time.

    Why: the cost structure is a genuine trade-off — softer tyres are faster but degrade sooner, each stop costs 22 s — and search finds the provably optimal plan under an explicit model rather than a heuristic guess. Comparing five algorithms on the same problem shows the optimality/efficiency trade-off with real counts.

    Run it

    python scripts/run_search.py

    How it works, step by step

    1. State

      RaceState is a frozen dataclass: lap, compound, tyre age, stops made, fuel, and the set of compounds used. key() buckets fuel to one decimal so floating-point noise does not split identical states in the explored set.

    2. Actions and transitions

      actions returns RUN, or PIT(compound) for each different allowed compound while stops remain and it is not the last lap. result applies one: a pit stop resets tyre age, adds the compound to the used set and counts the out-lap as a lap.

    3. Cost model

      step_cost is the time the action adds: lap_time = compound base pace + linear degradation (plus an extra 2.5× the degradation rate for every lap past the compound's cliff), scaled up on a track hotter than 30 °C, + a fuel-weight penalty; a pit adds the pit loss to an out-lap on fresh tyres.

    4. Goal

      is_goal requires the full distance and, in a dry race, at least two distinct dry compounds — the real F1 regulation.

    5. Algorithms

      BFS (FIFO) and DFS (LIFO with a depth bound) are uninformed. UCS, Greedy and A* share one _best_first core that differs only in the priority: g(n), h(n) or g(n)+h(n). It uses a heap with a counter tie-breaker for determinism and skips stale entries when a cheaper route to a state was found.

    6. Admissible heuristic

      heuristic = laps remaining × fastest fresh-tyre base pace. No lap can be faster than that, and it ignores degradation, fuel and any mandatory stop, so it never overestimates — which is what makes A* optimal.

    7. Measure

      _instrument wraps each run with time.perf_counter and tracemalloc for wall time and peak memory; comparison.compare tabulates cost gap, nodes expanded and frontier size.

    What and why

    Practical 5 builds candidate features from the clean laps, defines the three targets, and selects 45 features for lap time and 8 for the pit decision over 995 modelling rows.     Run it

    python scripts/build_features.py

    How it works, step by step

    1. Targets

      add_targets adds target_laptime, target_pit_next_lap (1 when the stint index rises on the next lap — the lap before the stop, which is the decision point) and a fuel-corrected lap time from a fitted linear fuel coefficient.

    2. Six feature blocks

      engineer_features, with a recorded reason for each feature: A tyre/stint (tyre life, its square, compound × tyre-life interactions); B race progress; C the driver's own recent pace as gap-to-field, strictly causal via shift(1) before rolling; D field pace (previous-lap median and trend); E environment (air temp, track–air delta, humidity, wind, a mean-centred temperature × tyre-life interaction); F one-hot compound, team and driver with one reference level dropped.

    3. Trim the warm-up

      trim_warmup drops opening laps where history features are undefined, keeping the two frames aligned row for row.

    4. Funnel stage 1–3

      Near-zero variance (near_zero_variance), then correlation above 0.95 — mutual information decides which of a pair survives (prune_correlated) — then VIF ≤ 10 on continuous columns only (prune_by_vif; a rare dummy always looks collinear with its group). On this data the funnel dropped: is_rainfall (near zero variance), tyre_life_sq (correlation), air_temp (correlation), track_air_delta (correlation), race_progress (vif).

    5. Funnel stage 4 — rank and choose K

      rank_features averages three notions of importance by rank: mutual information, random-forest importance and the L1 (Lasso / L1-logistic) coefficient. rank_with_stability records how many lap-forward folds put each feature in their top 12. choose_regression_features sweeps K and keeps the smallest K within 2% of the best CV MAE; classification fixes K = 8 because ~5% positives make a sweep noise.

    6. Write the contract

      build_metadata records the selected features per target, each feature's provenance, which features need scaling, the leakage exclusions and the validation strategy; FeatureContract gives later code a typed view over it.

    Practical 6 of 10 · app/intelligence/ml/

    Machine Learning

    10 classical models, time-aware validation, tuned thresholds and a generalisation guard.

    What and whyHow it works, step by stepTechnologiesKey functionsCode walkthroughOutputs and examplesApplicationsKey points & viva

    What and why

    Practical 6 trains and compares classical models for both targets: linear/logistic regression, decision tree, random forest, SVR/SVM and XGBoost. The selected lap-time model is svr (test MAE 0.781 s, R² 0.302) and the selected pit model is random_forest (test PR-AUC 0.250 at a tuned threshold of 0.4803).

    Why it is built the way it is: the data is a time-ordered panel, so a shuffled K-fold would train on lap 50 and validate on lap 10. Every model is validated on expanding-window, lap-forward folds and tested once on a chronological holdout (the last 20% of laps). Scalers are fitted inside each fold's pipeline. Pit stops are rare, so ROC-AUC alone would flatter the classifiers; PR-AUC, F1 and a tuned threshold are reported alongside it.

    Run it

    python scripts/build_all.py   # or: python -c "from app.intelligence.ml import pipeline; pipeline.train_all()"

    How it works, step by step

    1. Load and police the contract

      data_contract.load_and_validate checks that the selected columns exist, that no leakage column is present, and that there are no missing values; build_task_frame makes one frame per target.

    2. Split by time

      chronological_holdout reserves the last 20% of unique laps, keeping whole laps on one side. expanding_window_folds cuts the remaining laps into 5 blocks: fold i trains on blocks 0..i−1 and validates on block i.

    3. Preprocess inside the pipeline

      build_preprocessor is a ColumnTransformer: continuous features are median-imputed and — only for models that need it (linear, SVM) — standard-scaled; binary indicators pass through unscaled. Because it sits inside the sklearn Pipeline, it is re-fitted on each fold's training rows.

    4. Tune

      run_expanding_window_search is a custom grid search rather than GridSearchCV, so a fold that fails (e.g. a single class in training) is recorded as an error instead of aborting, and a fold where a metric is undefined is excluded from the mean, not counted as zero. The winner is refitted on the whole development set.

    5. Tune the decision threshold

      tune_threshold picks the probability cut-off on pooled out-of-fold predictions (never the test set), maximising F1 by default; an expected-cost objective with a missed pit costing 5× an early stop is also supported. 0.5 is only optimal for balanced classes with equal error costs — neither holds here.

    6. Select, with a guard

      rank_regression_models ranks by CV MAE; _apply_generalisation_guard overrides the CV winner only if its holdout R² is negative while another model's is positive — and says so in the report.

    7. Persist and register

      Pipelines are saved with joblib; write_registry records every model in model_registry.json, which the API reads to know which models exist.

    Key points & viva

    Why expanding-window validation instead of K-fold?

    The data is a time-ordered driver × lap panel. Random K-fold would train on later laps and validate on earlier ones, so every score would be optimistic. Lap-forward folds put the model in the situation a real strategy model is in.

    What does a negative test R² mean here?

    The model does worse on the closing laps than predicting the training mean — a different fuel and tyre regime from training, not a bug. The generalisation guard stops such a model being selected when another one generalises.

    Why tune the threshold instead of using 0.5?

    0.5 is only right for balanced classes with equal error costs. Pit stops are 48 of 995 laps, so the cut-off is chosen on pooled out-of-fold predictions.

    Extension — what do the quantum models show?

    Three PennyLane models on the noiseless default.qubit simulator, on the same split and metrics: features PCA-reduced to 4 qubits (81.8% of variance kept). The only defensible claim is a narrow comparison with classical models given the same inputs — not a quantum speed-up, not better models, and nothing about real (noisy) hardware.

    1. Runtime

      prepare_dl_runtime selects Keras 3's PyTorch backend before keras is imported — TensorFlow publishes no wheel for the Python version this project targets.

    2. Build

      _hidden_stack stacks Dense(ReLU) + Dropout layers with an L2 regulariser. build_regression_mlp adds a linear head (MSE or Huber loss); build_classification_mlp adds a sigmoid head (binary cross-entropy).

    Explainable AI

    SHAP, LIME, counterfactuals, a trust score and per-group performance — for both model families.

    What and whyHow it works, step by stepTechnologiesKey functionsCode walkthroughOutputs and examplesApplicationsKey points & viva

    What and why

    Practical 8 explains why the Practical 7 networks and Practical 6's selected models predict what they do, globally (which features matter overall) and locally (why this lap). It adds a trust score per prediction and a performance breakdown by driver, team and compound.

    Why several methods: each has a blind spot. SHAP's exact tree explainer is available only for tree models, so the network uses sampled KernelSHAP; LIME is a local linear surrogate that can disagree with SHAP; counterfactuals answer the engineer's actual question ("how many more laps until it says pit?"). Agreement between them becomes one component of the trust score.

    Run it

    python -c "from app.intelligence.xai import pipeline; pipeline.run_all()"

    How it works, step by step

    1. Load what to explain

      loading.load_target loads the network, the classical model and the same holdout. If a model is missing it raises ExplainerUnavailableError — it never substitutes a stand-in. pick_representative_rows chooses laps worth explaining (fastest, slowest, the actual pit lap, the one closest to the decision boundary, ...).

    2. SHAP

      tree_shap gives exact Shapley values for tree ensembles; kernel_shap samples them for the network over a k-means background of 25 points with nsamples=200. global_ranking is mean |SHAP|.

    3. LIME and permutation importance

      lime_analysis.explain_row fits a local surrogate; top_features maps LIME's discretised conditions (tyre_life > 12.00) back to feature names so its top-3 can be compared with SHAP's. permutation_importance measures the score lost when a column is shuffled.

    4. Physically consistent counterfactuals

      tyre_age_scan sweeps tyre age across the training range in 0.5-lap steps. consistent_tyre_age_rows recomputes every feature derived from tyre age (the compound interactions and the temperature interaction) so each probe is a lap that could exist — moving tyre_life alone would not be. DiCE runs as a time-bounded supplementary check.

    5. Trust score

      trust.compute combines confidence (distance from the tuned threshold), agreement between the network and the classical model, SHAP–LIME top-3 Jaccard overlap, and the share of inputs inside the training 1st–99th percentile. Weights are confidence 0.35, model agreement 0.25, explanation stability 0.20, input validity 0.20; a missing component is dropped and the rest renormalised, never scored as zero.

    6. Stratify and narrate

      stratification.stratify and fairness.assess report error or recall per driver, team and compound, flagging small groups; narrative.py writes the plain-English sentence an engineer would read.

    Key points & viva

    How do you know a SHAP explanation is not misleading?

    The tree model uses exact TreeExplainer; the network's sampled KernelExplainer values are labelled approximate (compare rank and sign, not magnitude); LIME runs on the same rows as a second opinion and its local_r2 is reported. SHAP explains what the model does, not what is true — which is why the fairness assessment exists.

    Why SHAP and LIME, and why two SHAP explainers?

    Exact when possible, model-agnostic when necessary. SHAP–LIME disagreement is a signal, and the trust score uses it.

    Is the trust score principled or arbitrary?

    Its components are real failure modes — distance from the tuned threshold, model agreement, explanation agreement, familiar inputs. Its weights (confidence 0.35, model agreement 0.25, explanation stability 0.20, input validity 0.20) are a documented judgement, not a fit, and are exposed in trust.WEIGHTS so they can be challenged.

    Why does DiCE have a time budget?

    Its random search can sample for a long time without finding an opposite-class row when pit laps are rare. It is capped at 60 s, starts from the row closest to the boundary, and stays inside each feature's training range; running out of budget is reported, not hidden.

    A counterfactual says "not reachable" — is that a failure?

    It is a result: sweeping tyre age across its whole training range never crosses the threshold, so the decision depends on combinations of features, not tyre age alone.

    What and why

    How it works, step by step

    1. Validate

      RaceStateRequest (Pydantic) rejects inconsistent states — current_lap ≤ total_laps, tyre_age ≤ current_lap — and the router checks driver, team, compound and model choices against the live dataset and registry. Failure is a 422.

    2. Construct features

      build_feature_row maps the race state onto the exact selected features: tyre life, race progress, compound one-hots and interactions, driver/team one-hots; anything it cannot derive is median-filled and listed as approximated. _flag_out_of_range warns when a derived value is outside the training range.

    3. ML, rules, DL

      _run_ml predicts with the registered Practical 6 pipelines; _run_expert_system runs Practical 2's forward chaining on a 16-key input dict; _run_dl runs the Practical 7 networks at their tuned threshold (never 0.5).

    4. Search

      _run_search runs A* (Practical 3) over the remaining laps from the current compound.

    5. Recommend

      _combine_recommendation: a fired expert-system pit_decision wins outright; otherwise ML and DL are compared — agreement is used, disagreement is reported (disagreement: true) and falls back to ML. A pit verdict is refined into PIT NOW / PIT IN N LAPS from the A* plan's first pit action.

    6. Explain (opt-in) and report

      With explain=true, Practical 8's explain_feature_row attaches SHAP factors and a trust score. POST /api/strategy/report renders the same analysis as a Markdown or HTML briefing.

      app/api/main.py registers the routers, restricts CORS to an allow-list, and mounts only the artifact folders the frontend reads (model files are never served).     How it works, step by step

    1. Functional testing

      functional_testing runs the real pytest suite with coverage and counts results from its --junitxml output — the plain summary line disappears when coverage reports are requested, so stdout is not scraped.

    2. Performance

      performance_evaluation confirms empirically that Practicals 6 and 7 use the same holdout (_verify_shared_holdout), consolidates every model's metrics, and times 200 strategy requests with and without explanations.

    3. Domain validation

      domain_validation replays the real race lap by lap through the API and compares pit calls with the stops drivers actually made: 934 laps replayed, pit-call precision 0.125, recall 0.872. It also checks which rules can fire through the live pipeline (_rule_base_reachability).

    4. Explainability validation

      explainability_validation checks SHAP top-feature stability, a faithfulness ablation (does removing the top feature move the prediction more than a random one?) and traceability.

    5. Responsible AI

      responsible_ai_assessment measures robustness (how often small perturbations flip the recommendation), per-team/driver/compound performance, transparency and human oversight. rai_service.py serves a live version for the dashboard's Responsible-AI page, with confidence shown only where a model natively produces one (probabilities, tree spread, Monte-Carlo dropout).

    6. Deployment readiness and future work

      deployment_readiness checks Dockerfiles, the health endpoint, the test result and scans for hard-coded metrics; future_enhancements records the plan.

    7. Documentation

      User manual, SRS, SDD, testing report and deployment guide live in docs/ and are consolidated in this study guide's first tab.

    State-Space Formulation

    Generated 2026-09-27 17:42 UTC.

    Problem as search

    Race-strategy selection is modelled as a shortest-path search whose solution is the sequence of per-lap decisions (run / pit-and-fit-compound) that completes the race distance in minimum estimated total time.

    Formal components

    Component Definition
    State (lap, compound, tyre_age, stops_made, fuel_kg, compounds_used)
    Initial state lap 0, start compound, age 0, 0 stops, full fuel
    Actions RUN (one lap on current tyres); PIT(compound) (fit a new compound, run the out-lap)
    Transition RUN: lap+1, age+1, fuel−burn. PIT: lap+1, new compound at age 1, stops+1, fuel−burn
    Step cost estimated lap time (compound, age, fuel, track-temp) + pit-loss if pitting
    Goal test lap == total_laps and (dry race ⇒ ≥ 2 dry compounds used)

    Cost model

    Lap time is a transparent, deterministic function:

    lap_time = base_pace(compound)
         + deg(compound) · tyre_age · temp_factor      (with a 'cliff' past cliff_age)
         + fuel_kg · fuel_time_penalty

    Softer compounds have lower base_pace (faster) but higher deg (wear faster), creating the pace-versus-durability trade-off that makes pit strategy non-trivial.

    Heuristic (for informed search)

    h(state) = (total_laps − lap) × fastest_possible_lap

    This is admissible: no lap can be completed faster than the fastest fresh-tyre pace at zero fuel, and the heuristic ignores the (non-negative) mandatory pit loss a dry race may still require — so it never overestimates the true remaining cost. Admissibility guarantees A* returns a cost-optimal solution.

    Goals (per the task specification)

    • Maximum points / optimal finish position — approximated here by minimising total race time, the dominant determinant of finishing position in a time-trial sense.
    • Minimum race time — the direct search objective.

    Generated 2026-09-27 17:57 UTC.

    Read this first. These are small variational circuits simulated exactly on a classical computer, trained on one Grand Prix. There is no quantum hardware in this project and nothing here demonstrates a quantum advantage — a noiseless simulation of 4 qubits is something a laptop does easily, which is the whole reason it is possible to run this experiment at all.     How the comparison was kept fair
    Data the Task 5 feature matrix, loaded through Task 6's own data contract

    Discussion

    Pit decision. The best quantum model on cross-validation is vqc (CV PR-AUC 0.3037), which is ahead of the parameter-matched classical model logistic_regression (reduced inputs) (0.2047) on the identical reduced inputs. Task 6's random_forest, which sees every selected feature, reaches 0.3863 on the same folds.

    On the test laps every classifier is judged on 1 pit event(s), so the test columns should not decide anything. That limitation is the dataset's, not the models'.

    Lap time. vqr reaches CV MAE 1.7459 s against 1.6243 s for linear_regression (reduced inputs) on the same 4 PCA components — worse than the matched classical model by 0.122 s. Test MAE is 1.1044 s for the circuit and 0.7815 s for Task 6's svr on all features.

    A circuit whose output is a single Pauli-Z expectation is bounded in [-1, 1] and has a few dozen parameters, so it is closer in capacity to a linear model than to Task 6's ensembles or Task 7's network. Reading it as "quantum is worse than classical" would be the wrong lesson; reading it as "a 26-parameter model with 4 compressed inputs cannot match a 45-feature ensemble" is the right one.

    What this experiment cannot tell you

    • Nothing about quantum advantage. default.qubit simulates the circuit exactly. Any speed comparison in the table favours whichever model has fewer parameters to fit, not whichever is running on better hardware — there is no quantum hardware here.
    • Nothing about scaling. 4 qubits and a 16-dimensional state space is small enough to simulate in milliseconds. The interesting regime starts where simulation stops being possible, and this dataset never gets there.
    • Nothing generalisable about F1. One race, one circuit, 995 laps, one labelled pit stop in the holdout. Every caveat that applies to Tasks 6-8 applies here too.
    • Noise is absent. Real devices decohere. A model that trains cleanly in simulation may not survive contact with hardware, and this project makes no claim that it would.

    Saved model format

    Every trained pipeline is saved with joblib.dump as artifacts/models/{laptime,pit_decision}/<model>.joblib. .joblib is the pickle format scikit-learn recommends for estimators — the same pickle protocol with more efficient handling of large NumPy arrays — so no separate .pkl copy is exported. Load one with joblib.load(path), or through app/services/model_cache.py as the API does.

    Selection criteria

    Task Primary Secondary
    Lap-time regression CV MAE (lower better), subject to a generalisation guard CV RMSE, CV R², test R²
    Pit-decision classification CV PR-AUC (higher better) CV ROC-AUC, CV F1, precision/recall

    Selection uses cross-validated metrics, not a single holdout number, and a model is only preferred over another when it wins on the primary metric computed identically across the same lap-forward folds.

    Why PR-AUC and not ROC-AUC for classification. Pit events are 4.8% of laps. At that prevalence ROC-AUC is dominated by the majority class and stays near 0.98 for a model that never fires — it measures ranking, not usefulness. PR-AUC asks the question that matters: of the laps this model flags, how many are real pit windows?

    The generalisation guard. Selecting purely on CV MAE once shipped a model with a negative test R² — worse than predicting the training mean — while a candidate with positive test R² sat unselected. The guard refuses to select a negative-R² model when a positive-R² candidate exists, and states plainly when it has overridden the CV ranking.

    Decision thresholds are tuned, not assumed. Each classifier's cut-off is chosen on pooled out-of-fold CV predictions rather than left at sklearn's default 0.5, which is only optimal for balanced classes with equal error costs. Neither holds here. Per-model thresholds appear in the table below.

    How this differs from the SHAP report

    LIME does not compute Shapley values. It perturbs the row being explained, asks the real model what it predicts for each perturbation, and fits a weighted linear surrogate to those answers in the neighbourhood of that row. The reported weights are that surrogate's coefficients.

    SHAP LIME
    Question answered How is credit for this prediction fairly divided? What simple model behaves like the real one around here?
    Basis Shapley values (game theory) Local weighted linear regression
    Guarantee Attributions sum to (prediction - base value) None; quality is reported as the surrogate's R2
    Output units Same units as the model output Surrogate coefficients on discretised conditions

    local_r2 is the diagnostic that matters: a low value means a straight line is a poor stand-in for the model near this row, so the LIME explanation should be discounted regardless of how confident it looks.

    Task 8 - Trust Score Report

    Generated 2026-10-18 17:17 UTC.

    A project-defined score, not a validated or standardised measure: the weights are a judgement, and it has not been checked against a race engineer's own assessment.

    The formula

    trust = ( 0.35 * confidence
        + 0.25 * model_agreement
        + 0.20 * explanation_stability
        + 0.20 * input_validity )
        / (sum of the weights of the components that apply)
    Component Weight Definition Why it is in the score
    confidence 0.35 Classification only: distance from the model's tuned decision threshold t (never 0.5), scaled to 0 at t and 1 at certainty — (p - t) / (1 - t) above t, (t - p) / t below it. Not defined for lap time, which has no decision boundary. A prediction sitting on the decision point is unusable however well explained.
    model_agreement 0.25 Classification: 1 - abs(p_dnn - p_classical). Regression: 1 - min(1, abs(dnn - classical) / target_std). Two model families trained on identical folds agreeing is real evidence; disagreement means at least one is wrong.
    explanation_stability 0.20 Jaccard overlap of SHAP's and LIME's top-3 features. If two explanation methods disagree about why, the explanation shown to the engineer is not trustworthy even if the prediction is right.
    input_validity 0.20 Share of the row's inputs inside the training data's 1st–99th percentile. Below 1 means the model is being asked about race states it did not learn from.

    A component that does not apply is left out and the other weights are renormalised — never scored as zero. For lap time confidence never applies, so its score is (0.25·model_agreement + 0.20·explanation_stability + 0.20·input_validity) / 0.65. The live API skips LIME, so explanation_stability is left out there too.

    Weights: {'confidence': 0.35, 'model_agreement': 0.25, 'explanation_stability': 0.2, 'input_validity': 0.2} — app.intelligence.xai.trust.WEIGHTS, exposed so they can be challenged and changed.

    What the bands mean to a race engineer

    Score Band Meaning
    >= 0.75 HIGH The two model families agree, the prediction is clear of the decision point, the explanations concur and the inputs are familiar. The strongest support this project-defined score can give - still not a guarantee.
    0.50 - 0.75 MODERATE Usable as one input among several. Read the SHAP factors first; at least one component is weak.
    0.25 - 0.50 LOW A prompt to look at the evidence, not a recommendation. The models disagree, the explanations do, or the inputs are unusual.
    < 0.25 DO NOT ACT The prediction sits on the decision point and/or the model families contradict each other.

    Implementation — the rules we held to

    • No leakage. Sector times sum to the lap time — excluded, and a test fails if one reaches a training matrix.
    • Time-aware validation. Expanding-window lap-forward folds and a chronological holdout; never a shuffled K-fold.
    • Scalers inside each fold, never fitted on the whole dataset.
    • Tuned thresholds. Pit cut-offs chosen on out-of-fold predictions, because 0.5 is wrong for 4.8% positives.
    • Honest gaps. When a metric is undefined the UI and reports say so, and why.
